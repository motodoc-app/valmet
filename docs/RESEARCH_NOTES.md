## 2. The terms are not interchangeable

| Term | What it is | Typical inputs | Typical outputs | Relation to our demo |
|---|---|---|---|---|
| **Point cloud** | Points sampled on surfaces, with position and often colour or intensity. A survey-grade cloud comes from registered laser scans (terrestrial or mobile/SLAM) or photogrammetry, with a known accuracy | Laser scanner or images; registration and control points | E57, LAS/LAZ, PTS, PLY | Our splat **centres** can be used as a pseudo point cloud (we do this for segmentation and navigation). They are optimisation results, include floaters, and have no stated accuracy. They are **not** a survey point cloud |
| **3D Gaussian splatting (3DGS)** | A scene made of many small 3D Gaussians, each with position, scale, rotation, opacity and view-dependent colour (spherical harmonics). It is trained from posed photos and is optimised for realistic rendering, not for exact geometry ([Kerbl et al. 2023](https://arxiv.org/abs/2308.04079), [project page](https://repo-sam.inria.fr/fungraph/3d-gaussian-splatting/)) | Photos plus camera poses, usually from structure-from-motion such as [COLMAP](https://colmap.github.io/) | PLY with Gaussian parameters (our file) | This is our input |
| **Semantic object segmentation (ours)** | Geometry clustering of splat centres (plane fitting, DBSCAN, pipe merging) and then labels from a vision-language model that looks at renders | Splat PLY only | Oriented boxes with label, confidence and source. No clean per-object splat set and no mesh | Implemented (`segmentation.py`, `vlm_labeler.py`) |
| **Gaussian-object extraction** | Selecting the Gaussians that belong to one object so the object can be shown, moved or exported on its own. Done either interactively on renders (see §3.1) or by training extra per-Gaussian features from multi-view masks, for example [Gaussian Grouping](https://arxiv.org/abs/2312.00732), [SAGA](https://arxiv.org/abs/2312.00860), [Feature 3DGS](https://arxiv.org/abs/2312.03203) | Interactive: trained scene. Training-based: the source photos, poses and 2D masks or features | A smaller PLY per object | Not implemented. Our oriented boxes are a rough proxy |
| **Scan-to-BIM** | Building an information model (typed objects with properties) from scan data. In the sources we found, most delivery is modelling by people in authoring tools, helped by semi-automatic tools | Registered, survey-grade point cloud, a scope and a level-of-detail specification | Native authoring files, IFC, 2D drawings | Not applicable to our unsurveyed splat without a new capture |
| **IFC (Industry Foundation Classes)** | An open data schema for built-asset information from buildingSMART. IFC 4.3 is published as ISO 16739-1:2024 (from search results and buildingSMART news; the ISO page returned HTTP 403 to us). It has classes for distribution elements such as pumps and valves (from our prior knowledge; the buildingSMART schema page returned 403, so **verify** class names before use) | A model from an authoring tool or code such as [IfcOpenShell](https://ifcopenshell.org/) (supports IFC2X3, IFC4, IFC4X3 per its site) | `.ifc` file | We could write our boxes to IFC (see §4.3). That is a format, not a BIM |
| **Navigable semantic floor plan** | A 2D or 2.5D map with walkable area, obstacles, labelled objects and routes | Floor and obstacle geometry, object labels | Grid or vector map, routes | Implemented: multi-level height field and A* (`navigation.py`), 2D plan fallback (`web/src/plan2d.js`) |

Short version: **3DGS is how the room looks. A point cloud is where surfaces are. Segmentation says what is where.
Gaussian-object extraction cuts one thing out. BIM and IFC describe what each thing is, as structured data, usually
with surveyed geometry. A navigable floor plan says where a person or robot can go.**

## 3. The references

### 3.1 gs-object-extraction (github.com/07LEE/gs-object-extraction)

**What we verified.** We read the README, `requirements.txt`, `pyproject.toml`, `third_party/README.md` and parts
of the code (cloned at commit `02ece47`, dated 2026-10-11, package version 0.4.0). The GitHub page showed 2 stars and
110 commits when we fetched it.

* Purpose, quoting the README: "Extract an object from a trained 3D Gaussian Splatting scene and export it as a
  standalone PLY. Open the scene in the viewer, click the object from a few angles, and SAM2 segments those views to
  identify the object's Gaussians. **No source photos are needed.**"
* Inputs: a scene "already trained with Graphdeco 3DGS, opened from its `point_cloud.ply`. Training is out of scope."
* Workflow: a desktop GUI. For each object you mark "about 16 views from around the object", extract, clean up stray
  Gaussians by hand, then export. It is **one object at a time, with a person in the loop**.
* Requirements: "A CUDA GPU, Python 3.10–3.12 and the CUDA Toolkit"; PyTorch (CUDA build); SAM2 from a pinned
  commit; `gsplat==1.5.3` (compiles CUDA kernels on first open); PySide6 for the GUI; a SAM2 checkpoint of about
  300 MB downloaded on first use.
* Licences: the tool is Apache-2.0. SAM2, the checkpoint and gsplat are Apache-2.0. PySide6 is LGPL-3.0/GPL; the
  README notes that a frozen bundle must meet LGPL terms.
* Stated limitation: "Surfaces missing from the source scene cannot be recovered: an object photographed from one side
  stays hollow on the other."
* A headless path exists (`gs_object_extraction/cli.py`), but it is an evaluation script for the 360-USID dataset and
  expects COLMAP cameras and object masks. The supported use is the GUI.

**Will it read our PLY?** By code inspection of `gs_object_extraction/ply.py`: it requires the property names
`x y z opacity scale_0..2 rot_0..3 f_dc_0..2` and a contiguous `f_rest_*` block for SH degree 0 to 3. Our header has
all of these (45 `f_rest` values, degree 3) and the loader reads by name, so the order in our file should not matter.
**We did not run it** (no CUDA GPU here). Not verified: whether the unknown "EGS" exporter uses the same conventions as
Graphdeco (quaternion order with `rot_0` as w, log scales, opacity as a logit). Our own loader assumes these and the
scene renders correctly in the browser, which is a good sign but not proof.

**What it would give us.** A real, photoreal cut-out of selected equipment (for example the P-005 pump set) that could
sit next to, or replace, the illustrative X-Ray model. It does not give names, asset ids, part breakdowns or internal
components.

**What it needs.** A machine with an NVIDIA CUDA GPU; setup of PyTorch, SAM2 and gsplat (time not measured by us);
manual marking and cleanup per object (time not measured); then our own step to move the result into our canonical
frame (`backend/xray/canonical.py` applies a rotation and floor offset) and into the web viewer.

| Verdict | |
|---|---|
| (a) Hackathon | **Not for the main demo.** Doing all 676 objects by hand is not possible overnight, and our container has no CUDA GPU. One object (P-005) is possible only if a team member already has a working CUDA machine, and it must be presented as an experiment. Nobody should block on it |
| (b) Pilot | **Worth a structured trial** on 5–10 key items, with time per object recorded. Batch use would need scripting around the GUI or a training-based method (Gaussian Grouping, SAGA), and those need the source photos and poses, so the capture must keep them |

## 4. Why a full conversion is not feasible before tomorrow

### 4.1 Full Gaussian-object extraction
* The interactive tool works one object at a time with about 16 marked views plus cleanup. 676 objects is far beyond
  one night, even before setup.
* Training-based methods (Gaussian Grouping, SAGA, Feature 3DGS) need the source photos and camera poses to train
  per-Gaussian features. **We have neither**, so they cannot run.
* Our build container has no CUDA GPU; every tool above requires one.

### 4.2 BIM conversion
* Scan-to-BIM needs a registered point cloud with known accuracy. Our scale is approximate and not surveyed.
* It needs modelling time (by people, or automated only for room shells) and, for a service, procurement and an NDA.
* A BIM made from our splat would look precise but rest on unsurveyed geometry. That would mislead users.

### 4.3 What is feasible tonight (optional, small)
* **Rough per-object cut-outs without a GPU (inferred, not built).** We already have each object's oriented box
  (`scene_objects.json`). Selecting the splats of the scan that fall inside one box would give a crude cut-out for
  the X-Ray view. It would include floor and neighbour splats. It must be labelled "rough box crop from the scan".
* **IFC-shaped export of our boxes (inferred, not built).** IfcOpenShell can write each box as an IFC element with
  its label, confidence and asset id. That is a few hours of work and testing. It would be an interchange file, not a
  BIM, and should carry "unsurveyed, automatic" in its properties. We recommend leaving it to the pilot unless the
  judges ask for IFC.

## 5. Recommended staged path for a pilot

| Stage | What | Needs | Exit check (measure, do not assume) |
|---|---|---|---|
| 0 (now) | Splat scene, automatic object boxes and labels, navigation, grounded copilot on synthetic data | What we have | Demo works end to end |
| 1. Capture with poses | Capture the site again and **keep the photos, camera poses and capture log**. Add a small number of surveyed control points, or a laser scan of the same room, to fix scale and check accuracy. Train the 3DGS scene ourselves so we hold every input | Camera or scanner, site access and permits, a CUDA GPU for training, a data agreement with the site | Scale error against control points; share of the room covered |
| 2. Per-object Gaussian extraction | Extract key equipment (start with 5–10 items). Compare the interactive tool (§3.1) with a training-based method that uses the kept photos. Confirm each object's identity in the field (QR/NFC, already in the workbook's `identity_methods`) | Stage 1 data, GPU, a reviewer | Minutes per object; share of objects accepted by a reviewer without edits |
| 3. IFC export of key equipment | Write the confirmed equipment as IFC elements with asset id, tag, class and source, plus the room shell (automated, §3.5). Geometry from the surveyed data, not from splat boxes | IfcOpenShell or an authoring tool; Valmet's IFC requirements | Opens in the viewers Valmet uses; property set agreed with Valmet |
| 4. Live, read-only data | Connect the asset register, work orders and condition data through read-only adapters | See [`DATA_INTEGRATION.md`](DATA_INTEGRATION.md) | Provenance and staleness shown on every value |

Two formats are listed in the workbook's `Public_Research` sheet for exchanging splats themselves: glTF Gaussian
splatting (Khronos) and OpenUSD particle fields (NVIDIA). We have not evaluated them.
